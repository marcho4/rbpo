# NFR

### Feature 1: Ограничивать кол-во созданий компаний

#### Scenario
Пользователь создал 5+ компаний внутри окна 10 минут

#### Given
аутентифицированный пользователь без активной блокировки
And с начала текущего 10-минутного окна он создал 5 компаний
#### When
Создано больше 5 компаний
#### Then
Блокировка на 10 минут + Лог + Алерт

### Feature 2: Ограничить получение всех данных по методам GET /leads чаще 2 раз в секунду

#### Scenario
Пользователь превышает лимит 2 запросов в секунду к списку лидов

#### Given
аутентифицированный пользователь без активной блокировки и с лимитом 0 запросов в текущой секунде
#### When
он выполняет третий запрос GET /leads в течение одной секунды
#### Then
сервис отвечает статусом 429 Too Many Requests
And создаётся запись в журнале безопасности с типом `rate_limit_violation`

### Feature 3: Доступ к данным для каждого человека только при наличии валидного токена авторзиации

#### Scenario
Запрос без валидного токена
#### Given
неаутентифицированный пользователь (отсутствует или просрочен JWT-токен)
#### When
он запрашивает любой защищённый эндпоинт (например, GET /companies)
#### Then
тело ответа содержит описание ошибки `invalid_credentials`

### Feature 4: Время ответа сервиса не более 200 ms при 100 rps на перцентиле 95

#### Scenario
Нагрузочное тестирование сервиса
#### Given
система находится под нагрузкой 100 запросов в секунду в течение 5 минут
#### When
собирается статистика времени ответа
#### Then
95-й перцентиль времени ответа не превышает 200 ms

### Feature 5: Логирование ошибок в приложении

#### Scenario
Необработанное исключение во время выполнения запроса

#### Given
запущенный сервис с настроенным уровнем логирования WARNING+
#### When
во время обработки запроса происходит необработанное исключение
#### Then
в журнал пишется запись уровня ERROR с полным stack-trace
And метрика `error_count` увеличивается на 1

### Feature 6: SLA сервиса 99% времени

#### Scenario
Расчёт доступности за последние 30 суток
#### Given
собраны данные мониторинга аптайма за последние 30 дней
#### When
рассчитывается процент доступности
#### Then
суммарное время недоступности не превышает 7 часов 18 минут (1 %)

### Feature 7: Ограничение на изменение лидов и компаний чаще 5 раз в минуту

#### Scenario
Пользователь превышает лимит изменений
#### Given
аутентифицированный пользователь выполнил 5 операций изменения лидов/компаний за последнюю минуту
#### When
он пытается выполнить шестую операцию изменения в том же минутном окне
#### Then
сервис отвечает статусом 429 Too Many Requests
And событие записывается в журнал безопасности

### Feature 8: Шифрование конфиденциальных данных «на покое»

#### Scenario:
Запись чувствительных данных в базу
#### Given
база данных полностью инициализирована и включено шифрование на уровне файла/колонки
#### When
сервис сохраняет чувствительные поля (например, refresh_token)
#### Then
данные записываются в зашифрованном виде с использованием AES-256
And без ключа расшифровки чтение напрямую из БД возвращает нечитаемое значение
